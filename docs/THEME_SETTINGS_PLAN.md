Status: proposed. Owner: lead. Companion files: `docs/PAGE_ENCAPSULATION_CHECKLIST.md` (per-page task board), `docs/CODE_REVIEW_RULES.md` (review rubric).

ESLint currently excuses this debt instead of preventing it:

- `eslint.config.js:183-187` exempts three files from the style rules (`src/features/ai/chat/AiChatPage.tsx`, `src/features/**/dialogStyles.ts`, `src/features/**/dialogShared.ts`). `AiChatPage.tsx` still hardcodes `backgroundColor: "#FFFFFF"` - exactly what the rule would catch were the file not exempt.
- `eslint.config.js:179` turns `no-restricted-syntax` off for `src/styles/shared.ts`.

Consequence: the design system exists (`@/components/ui` 23 exports, `@/components/common` 41 exports) but pages bypass it, so a global theme setting cannot restyle the app.

## 2. Goal and definition of done

Ship a simple theme-settings panel, in the style of commercial template packages, whose settings restyle every page **without editing any page source**. That property is the operational definition of "components are encapsulated", and it is testable.

Done means all of:

1. ESLint enforces the page-layer rules with no hand-written escape hatches; the only exceptions are entries in a ledger that can only shrink.
2. `src/features/settings/**` provides theme settings that a user can change at runtime.
3. All 64 debt pages are converted; the ledger reaches zero.
4. The encapsulation test passes: mutating the theme changes rendered output on every page with zero source changes.

## 4. Page-layer rules (target)

"Page layer" means `src/features/**/*Page.tsx`. Forbidden there:

| Forbidden                                                                | Rationale                                                   | Replacement                                                           |
| ------------------------------------------------------------------------ | ----------------------------------------------------------- | --------------------------------------------------------------------- |
| `makeStyles`                                                             | layout decisions must live with the component, not the page | primitives + props                                                    |
| `style={{...}}`                                                          | same                                                        | `gap` / `align` / `justify` / `variant` / `density` / `surface` props |
| literal px, hex, radius                                                  | values must come from the token layer                       | `theme.*` (and later the settings provider)                           |
| `import { theme } from "@/styles/theme"`                                 | a page must not know token names                            | component reads the token                                             |
| importing the settings config/store                                      | a page must not branch on config                            | provider applies config; page stays declarative                       |
| conditional styling (`style={cond ? a : b}`, `className={cond ? x : y}`) | style must not be decided by page-level conditionals        | `variant` prop, or a named component                                  |

Data/loading/empty/error branching in a page stays legal. The ban is on style and config branching, not on control flow in general.

**Scope: the page layer only.** `src/components/**` is unrestricted. Components are where styling legitimately lives, so no style rule may be applied there - not the rules above, not the existing hex/flex ones. These bans exist so that pages compose the component layer; they are not a constraint on the component layer itself. Concretely, a component file may call `makeStyles`, use the `style` prop, and hold literal px, hex and radius values.

## 5. Enforcement: the debt ledger (ratchet)

Turning the rules on today would produce hundreds of errors and break the pre-push gate, and a rule with no migration path is what produced the current escape hatches. So enforcement is ratcheted:

- `eslint.page-debt.json` maps a page path to the exact rule ids it is currently excused from.
- `eslint.config.js` reads that file and adds per-file ignores **only for those rule ids** - a hand-written exemption becomes a data entry instead.
- A meta test asserts three properties: no stale entries (every entry genuinely violates), no missing entries (every violating file is listed), and the entry count never increases against the committed baseline.
- Converting a page means deleting its entry. The test fails if an entry is re-added.

Baselines are committed numbers, and they move only with a stated reason. The recorded history is: 209 raw mappings at the first commit of the ledger, 187 after the literal rules were narrowed, and 212 after that narrowing was corrected (minus 25 wrongly-dropped px entries, plus 3 genuine conditional-style detections the widened tree walk found). A baseline that rises without such a reason is a loosening and fails review.

This keeps `npx eslint .` at zero findings at every step while guaranteeing the debt only shrinks.

## 6. Theme settings feature (B)

Location: `src/features/settings/**` (feature layer, as requested). Keep it small; this is the template-vendor pattern, not a design tool.

Settings, first cut: brand colour, light/dark, corner radius, density (compact | comfortable), sidebar layout (expanded | collapsed), content width.

Shape:

- a data-only store (`zustand` + persisted to localStorage) holding plain values; no JSX, no branching on styles;
- a provider that converts the values into a Fluent theme object plus CSS custom properties, and wraps the app under `FluentProvider`;
- a resettable panel UI that composes `@/components/common` and `@/components/ui` only and itself obeys every page-layer rule;
- pages never import the store or the config; they get restyled because they read `theme.*` through components.

## 7. The encapsulation proof (D)

One test, two assertions, run as a gate:

1. Render a page matrix (every page with debt, widened later to all pages) under N theme mutations: radius 0, density compact, spacing doubled, dark mode, brand swap. Assert the computed style actually changes per page.
2. Assert that the run touched zero source files, and that no page imports the settings store or config.

A page that does not react to the mutations is not encapsulated, and the test names it. This is the same technique used to mutation-test the wrapper layer earlier in this repo.

## 8. Sequencing

A -> B -> C -> D, with D's first version landing alongside B so the target is visible before the long tail starts.

A first because it is cheap, it makes the rules honest, and it stops new debt while C runs. B before C because B defines the vocabulary (variants, density, surfaces) that C converts pages onto; converting first would mean converting twice. D is written once B exists and then gates C.

### Per-page loop for C

1. Page worker converts exactly one page: remove `makeStyles`/inline styles, compose existing primitives, delete the page's ledger entry.
2. Page worker records evidence: lint, typecheck, unit, browser, computed-style before/after, ledger entry removed.
3. Reviewer independently reproduces the evidence against the rubric in `docs/CODE_REVIEW_RULES.md`.
4. Any finding goes back as a fix, then re-review. A page is only `done` after a clean re-review.
5. Checklist row updated (`Status`, `Owner`, `Review`, `Commit`), one commit per page.

## 11. Risks

- A ban without primitives creates escape hatches; every new rule in A must ship with the primitive it points at.
- Some layouts are genuinely bespoke. The target is rare, named and justified exceptions in the ledger, not zero exceptions.
- Runtime theming re-renders the tree. Acceptable for a settings panel, but do not use the store for per-page tweaks.
- 64 pages is a long tail. If throughput matters, pages that share an identical conversion pattern may be grouped into one commit, but each page still needs its own checklist row and review verdict.

## 12. Decisions

Settled; do not relitigate without a new reason.

1. **The panel is an end-user feature, kept simple.** It follows the template-vendor pattern: a small, fixed setting set that a user changes at runtime. i18n, keyboard access, labels and persistence are therefore hard requirements, but the setting set stays small - six settings, not a design tool.
2. **The component layer is unrestricted.** All style bans are scoped to the page layer (`src/features/**/*Page.tsx`). No style rule may be applied to `src/components/**`.
3. **The `#FAFAFA` card-surface rule stays as it is**, applying to all of `src/**` including components. Rationale: it is a value-duplication rule (one canonical surface colour), not a style-encapsulation ban. It does not restrict how a component styles; it forbids re-declaring one canonical value that already exists in `src/styles/shared.ts`. Removing it would be exactly the kind of arbitrary loosening that produced the current escape hatches.
4. **Import boundaries stay.** `@fluentui/react-components` only inside `@/components/ui`; raw `tokens` only in `src/components/ui/**` and `src/styles/theme.ts`; no i18n inside components. These are what make the wrapper layer a closed API, and they are not style bans.
5. **Design-system carve-outs are recorded, never implicit.** `src/styles/theme.ts`, `src/styles/shared.ts`, `src/components/ui/**`, `src/theme/**` and the barrel files are design-system infrastructure and stay free of the page-layer rules. Where one of them genuinely needs relief from a global rule, the config must express it narrowly (exclude that file from that specific selector) and this list must name it. A blanket rule-level `"off"` with no record is not acceptable.

## 14. Workstream C execution protocol

C converts the debt pages onto the composition pattern that workstream B proved.

**Batch policy, set from measurement rather than from the original estimate.** This section first said one page is one task. The measurements say otherwise. The pilot cost 22 minutes for a single page. Batch 1, run after the shared primitives and the shared parity helper existed, cost about 23 minutes for five pages, of which roughly 13 minutes was fixed task overhead (recon, probe authoring, base capture in a worktree, ledger, gates, commit) and about 1.5-2 minutes was marginal per page. Paying that fixed cost once per page does not make the work safer, it multiplies it.

So a task carries a batch of up to six pages of the same shape. What does not change, and is not negotiable, is that every page in the batch carries its own commit, its own parity test, its own ledger deletion, its own gates, its own review verdict and its own checklist row. One page per commit is what keeps a bad pattern revertable in isolation: it is the substitute for one page per task, not an omission. A batch whose diff cannot be reviewed page by page is a finding against the batch, not a shortcut.

Per-task shape:

1. **Selection.** Pages are taken one at a time in checklist order, grouped by feature, so a task never spans two features.
2. **Write scope.** The task declares the page file, the ledger and meta-test files, and the component-layer files that will hold any new primitive. A primitive that does not exist yet is added to `src/components/common/**` or `src/components/ui/**` inside the same task, and the task names it up front. A page never works around a missing primitive.
3. **The conversion.** The page is re-expressed with composition primitives. Creating a style module under `src/features/**` in order to satisfy the page rules is not a conversion and is a review blocker on its own: moving a `makeStyles` block from a page file into a sibling file changes nothing about the page's coupling, it only moves the text. Styles that a page genuinely needs belong to a primitive in the component layer, added in the same task. Raw `tokens` stay confined to `src/components/ui/**` and `src/styles/theme.ts`.
4. **Ledger, in the same commit.** The page's entries are deleted from `eslint.page-debt.json`, and the baselines in `src/eslint.page-debt.test.ts` are lowered to the new actual counts. During C the baseline may only move down. An upward move is a finding, not a bump.
5. **Worker gates.** `npx eslint .`, `npx tsc --noEmit`, `npm run test:unit`, `npm run format:check`, `npm run check:deps`, and the browser gate.
6. **Visual parity evidence.** Computed-style values for the converted page's route, before and after, captured at the base commit in a worktree. The assertion covers EVERY card and field row the page renders, not just the first one: batch 1's review measured only the first card of each page, so an anomaly confined to a later card would have been invisible to both the helper and the page test. It also covers the grid's computed layout rather than only the inline template, since a difference that appears after CSS resolution is still a visual difference.
7. **Review.** The reviewer independently confirms that the page has no ledger entry, that the rules really fire on it by injecting a violation and watching it fail, that rendering is unchanged, that no rule was weakened and that no suppression was added. The reviewer specifically confirms that the entry was deleted rather than the rule narrowed to fit, and that the page's styling now lives in the component layer rather than in a new file beside the page. A conversion whose diff is mostly a relocation is rejected, not accepted.
8. **Done.** A page is done only after the review passes. Its checklist row records the commit, the verdict and the reviewer.

Cadence:

The pilot page runs alone, end to end, to measure what a conversion actually costs. The cadence for the remaining pages is set from that measurement rather than estimated in advance. Per-page rigour is not negotiable - every page gets its own gates, its own parity evidence, its own reviewer verdict and its own checklist row. What the measurement decides is only how many pages share a worker task and a review window, never whether a page is verified.

### 14a. Props a page is allowed to pass

These rules exist because the batch that converted the checklist and data-collection pages hit a trap that cost a review cycle, and because the same trap would otherwise catch every remaining page one at a time.

`DetailCard` had grown a `titleVariant?: "section" | "compact"` prop. It renders correctly, it was tested, and no page could use it: `titleVariant="compact"` is an `i18next/no-literal-string` error inside `src/features/**`, and so is `titleVariant={"compact"}`. Only hoisting the string to a const escapes the rule, which is a dodge rather than a design. The prop was therefore dead API that advertised a capability pages could not exercise. It is removed; the compact title survives as `DetailCardTitle`, an exported component used as a card child.

The review that settled this also measured the justification first offered for the child form - that it was needed to keep the title a direct child of the card so the full-width bottom border matched. Both forms render the title as a direct child with byte-identical computed styles; the stated reason was false and the real reason was only the lint rule. Record the real reason, not a plausible one.

The rules, which apply to every remaining page and to any future primitive:

**R1.** A prop a page is expected to pass in JSX must be usable from a page with NO config edit. Either express the variation as a child or a variant component that takes no string-literal enum, which is the `DetailCardTitle` pattern, or - if a shipping page will genuinely pass a literal enum - add that attribute name to the `i18next/no-literal-string` exclusion list **in the same commit**, with a one-line justification that the prop cannot carry user-visible text.

**R2. Necessity test for an exclusion.** An exclusion may only be added for a prop that shipping page or component code already uses. `mb`, `tone` and `headerGap` qualified because pages use them today. An exemption for a prop with zero users is convenience and is rejected.

**R3.** Never hoist a const in a page purely to avoid the i18n rule.

**R4. Dead props.** A prop added for a page that ends up not using it is deleted in the same batch. Deleting an unused prop always beats widening an exclusion.

**R5. Reviewer gate.** Before a batch lands, the reviewer greps every new string-literal prop and every new primitive prop for use under `src/features/**`. Anything that would error there is removed, or exempted with a necessity justification, in the same commit.

**R6. A new generic prop must name its second consumer, in the commit message.** A prop, option or variant added to a shared primitive is justified by the number of call sites it serves, not by the difficulty of the page that prompted it. State the second consumer by name; if there is no second consumer today, the page reuses an existing primitive instead, or the variation is expressed as composition. This rule came out of the review of the `QueryDetailPage` deferral: the writer estimated six to eight new knobs were needed, and the reviewer checked them one by one and found about three to four real (overflow, shrink, chat bubbles - each with named consumers such as AiChatPage, the dialogs, and forty-eight shrink sites), while the rest were already covered by `Stack.p` (which takes raw shorthand such as `6px 0`), `KV`, `DetailCardTitle` with `Stack.mb`, `SidePanel.width` and `Input`. The one claim with no second consumer - a tinted, bordered surface variant - was the one that should reuse an existing component rather than be minted. Overstated primitive needs are the same failure as a dead prop: both spend the shared surface to make one page easy.

A related note on the same class of error: a new string-literal prop that a page _can_ use still needs its attribute name in the exclusion list, otherwise the page cannot compile under lint. Widening that list is a real change to the ruleset, so it is disclosed and reviewed like any other, and R2 decides whether it is allowed.

## 15. What the checklist is for

`docs/PAGE_ENCAPSULATION_CHECKLIST.md` is the task ledger for C, not documentation. It holds one row per page, with per-rule columns showing the debt that must reach zero and Status / Owner / Review / Commit columns recording the outcome. A row is authoritative only when its Commit column holds a sha and its Review column holds a reviewer verdict. The summary counts at the top are recomputed from the rows, and at the end of each wave the file is reconciled against `eslint.page-debt.json`: the two must agree, and any disagreement is a finding about the ledger rather than about the checklist.

## 16. Conversion recipe (writer handover)

Recorded so that losing a writer's context costs the project as little as possible. Any writer picking up a page starts here.

**Read first, in order.** The page file end to end; a page from the previous batch as a template pair (the page, its `.browser.test.tsx`, its `.parity.json`); the page's array in `eslint.page-debt.json`; and the baseline constants that must move with it - `LEDGER_FILE_BASELINE`, `LEDGER_MAPPING_BASELINE`, `LEDGER_RAW_MAPPING_BASELINE` in `src/eslint.page-debt.test.ts` and `RAW_MAPPING_BASELINE` in `src/eslint.page-rules.test.ts`.

**What a conversion removes.** The ledger enforces `local/no-page-makeStyles`, `no-page-style-prop`, `no-page-theme-import`, `no-page-literal-px` and `no-page-literal-radius`. A page is done when its own `makeStyles`, its theme import, its style props and its literal px and radius strings are gone and the primitives carry the styling.

**Which primitive a block becomes.** A section card with a semibold title and `14px 16px` padding becomes `DetailSectionCard` with `title={t(key)}` and children unchanged. A `Grid` with `gap="12px"` keeps Grid and takes `gap={12}`. A label and value row stays `KV`. A horizontal run stays `HStack`. Never introduce a new primitive, and never add a prop to a common primitive unless a second consumer already exists - that is R6, and the second consumer's name goes in the commit message. Keep `Text` only where it is the loading fallback. Delete `makeStyles`, the theme import and `useSharedStyles` once nothing references them; the compiler will say when.

**Order per page, one commit each.** Capture the fixture; convert; write the parity test; falsify; delete that page's ledger array and lower both baselines in the same commit; gates; commit.

1. **Fixture capture, in a worktree, never from converted output.** `git worktree add --detach /tmp/wt-<batch> <conversion-parent-sha>`, then `ln -s /root/fluent-enterprise-ui/node_modules /tmp/wt-<batch>/node_modules`. After every checkout, copy the current measuring code in again, because a checkout reverts tracked files: `cp src/test-utils.tsx /tmp/wt-<batch>/src/test-utils.tsx`. Put the harness in the worktree as an untracked `src/__capture.browser.test.tsx` and select the page with an imported constant rather than an environment variable - browser-mode modules do not see `process.env`, so env-based selection silently registers zero tests. Emit the capture as self-describing chunks through `expect.soft(payload).toBe("__capture__")` and reassemble with a small extractor. Run one vitest invocation per bash call, and `rm -rf node_modules/.vite` before re-running: the vite dep cache is symlinked into worktrees and a worktree run poisons it, which surfaces as `Failed to fetch dynamically imported module` or a run reporting no tests.
2. **The test passes `expected`** so the readiness wait anchors on the page's text: `capturePageViews({ includeDefault: true, expected: parity })`, or `captureWalkViews(parity)` for the `{ walk, views }` pages. Walk every view and every section. Never add a fixed sleep - they are gone from the tree and must not come back.
3. **Falsification is always on a LATER card or row, never the first.** Perturb one label and one value, run that page's test, show red, then restore and confirm `git diff` shows no page change. Older pages match `label[:=]\s*t\(`, so swap the key for another key that already exists rather than inventing one.
4. **Ledger and baselines move in the same commit** as the page: that page's array deleted, both baselines lowered by exactly that page's rule count and raw count. Baselines may only move down, and a new ledger entry is never added.
5. **Gates, with `tsc` FIRST** and then eslint, unit alone, `format:check`, `check:deps`. `tsc` is not in the commit hook - the hook runs eslint only - so running it after the commit is how a commit with type errors landed once.

A perturb-then-restore cycle needs an anchored or line-addressed restore. A writer renamed the first occurrence of an i18n key that also occurs elsewhere in the page, and the restore put the original key back onto the wrong one of the two, swapping two labelled rows instead of reverting them. `git diff` looked clean to it and the ordinary test still passed, because a swap preserves every metric; the browser chunk gate caught it, since the received fingerprint had the two rows in the opposite order. So restore by line or by anchored context, and rerun the page's test after restoring rather than trusting a diff check - and note that the chunk gate paid for itself here for a reason that had nothing to do with the race it was built for. The same rule governs edits during a conversion, and a writer hit it twice in one batch: inserting a wrapper by searching for the first line with a repeated prefix wrapped the wrong card and rewrote a type-only import, which `tsc` caught as an unbalanced element, and the page was reverted and redone with index anchors. Anchor on an index or on a unique full line, never on a prefix that repeats in the same file. Both defects were self-reported, and reverting rather than patching around a mis-anchored edit is what kept them one-line mistakes instead of silent corruption.

**Traps that have cost time.** A px constant passed to a primitive prop still trips `no-page-literal-px`; use `theme.spacing` or let the primitive own the value. Rebuilding a labelled value row with an inline-flex primitive grows the label box about 6px through the descender, which changes the fingerprint box - keep the existing primitive or fix the row's alignment rather than re-capturing. Reusing the existing `t(key)` from the block being replaced is how i18n stays clean; do not add literal user-visible strings or new keys in a batch. Commitlint body lines are capped at 100 characters. No comments under `src/**`, no `eslint-disable` or `@ts-ignore` family, do not touch `docs/**`, never `--no-verify`, never push, no repo-wide prettier. And a colour or box-metric difference is a real difference until a mechanism explains it: the last one that looked environmental was a stale mouse pointer leaving hover on whatever sat under it, so move the pointer before capturing and never dismiss a colour diff by re-running.

And never carry a grep line number into a script: grep prints 1-based lines while a script indexes 0-based, and a writer corrupted the page that way - only `tsc` caught it, and the redo used a content-anchored state machine over exact full lines. Either convert the numbers deliberately or match on content.

A conversion can also fail in a way a fingerprint cannot describe, and that is not a metric question. Shift-logbook's first conversion was type-clean and lint-clean and then threw `Cannot read properties of null (reading 'useContext')` at render, inside the error boundary, before any comparison ran. The writer stopped, parked the work outside the repo, reverted with `git checkout` and left the tree clean. That is the correct response to a crash during a conversion: the fixture is not the thing that is wrong, so there is nothing to re-capture and nothing to nudge, and `git status` must be empty before the next attempt.

Two more traps from batch 6. Do not clear a stale capture receiver with `pkill -f`: the pattern matches the invoking shell's own command line, so it kills the shell mid-chain and the capture silently never runs, which cost a writer a whole turn - give each capture its own port and receiver instead of killing anything. And the conversion parent does not have to be the immediately preceding commit: a docs-only commit in between leaves every page file identical, so capturing at that later commit is equivalent and should just be stated rather than treated as a discrepancy.

**Spacing and cards on a page whose styling is not yet on primitives.** This came up first on shift-logbook, a page carrying a literal-gap VStack, plain divs with `sharedStyles.contentCard` plus padding and margin style props, a `Text` with a top margin, and the theme import - seven sites, none of them already expressible through the primitives the way the earlier pages were. The policy, so that it is not re-asked per page: replace a titled card div with `DetailSectionCard`, which owns its padding; express vertical rhythm through the container's `gap` rather than through one-sided margins, since `gap` is the primitive's own mechanism; where a one-sided margin really is required, put `mb` on the preceding sibling rather than adding `mt` to `Stack`, because a new `mt` prop is new generic API and R6 would require a named second consumer before it can exist; and never add padding or margin classes to `src/styles/shared.ts` from a page batch. The parity fingerprint is the arbiter, and the failure mode is specific: a margin moved onto a sibling is equal only where margins collapse and no `gap` is also applying, so a geometry difference here is a real difference. It is not to be resolved by re-capturing the fixture.

**The section-card primitive is the outlier against its own corpus, and that is a design input rather than a page problem.** A survey of the 35 pages still carrying ledger entries found 20 that declare a card-ish style, and in those declarations `theme.spacing.lg` (16px) is the common case at 14 files while the literal `14px 16px` appears in exactly two. A whole family of nine look-alike detail pages - ShiftDefinition, ShiftLogbook, ShiftPlan, Site, SortRuleSet, Step, SubstrateMap, TransferOrder, TransferRequirement - declares exactly `{12, 16}`, 16 for the card and 12 for the rows inside it. `DetailSectionCard` hardcodes `padding: "14px 16px"` with no parameter, `DetailSurface` is a bare `contentCard` with no padding and no title, and `Stack` does carry `p`, `mb` and `minHeight` but not `mt`. So a 16px titled section card has no existing expression, which is why two pages stalled rather than a conversion failing.

The order of attack resolved the question on the evidence rather than on taste: composition is open, so no primitive changed. Shift-plan's sites all reduce to a `VStack` carrying the existing `sharedStyles.contentCard` class plus `p`, `gap`, `minHeight` and `mb` - every one of which already exists - with the surface, padding and minimum height on a single element rather than split across a wrapper and a child, because splitting them only stays equivalent under border-box sizing. Nothing there is genuinely 14px 16px, so `DetailSectionCard` is not used on that page at all. Adding a spacing-scale option to `DetailSectionCard` remains the honest shape if the corpus norm is ever to be represented by the primitive, and its default would have to preserve the current rendering so no converted page moves, but it is not added while composition suffices: a prop whose consumer does not land has to be deleted again, which is worse than a page waiting. The trigger to revisit is concrete - two pages that end up hand-composing the same titled 16px card, at which point the repetition itself is the second-consumer evidence.

**`contentCard` carries its own `margin-top: 10px`, so a page's margins must stay on the same element as its surface.** This is the root of the rhythm trouble on the two deferred pages and it cost real time to find. `sharedStyles.contentCard` is not a bare surface: it is `cardSurface` plus `flexGrow: 1`, `minHeight: 0` and a baked-in `marginTop: 10px`. So when a conversion moves a card's `marginBottom` onto a sibling as `mb`, or replaces it with the parent's `gap`, the result is not equal - the card's own 10px top margin is still there and the spacing becomes a sum rather than the same value. The fingerprint caught it as `10px 0px 12px` against `10px 0px 0px`. The rule is therefore narrow and mechanical: express a card's margins with `mb` on the element that already carries the surface, never on a sibling and never as a parent gap, and when the base node declares a margin shorthand, match the whole of it rather than one side of it. Padding is unaffected - `p` composed correctly and matched the base exactly on both cards.

**`Stack` is a flex container and its `gap` defaults to 12px, so substituting a `Stack` for a plain `div` is never layout-neutral - and this supersedes the earlier decision that composition was open.** That decision rested on a per-site analysis that assumed a `VStack` substitution was equivalent; the measurement says it is not. The fingerprint diff on shift-plan was `columnGap: normal` to `12px` and `rowGap: normal` to `12px` with node heights moving 2288 to 2312 and 1916 to 1928. Two separate effects are in play, and only the second is obvious. `Stack` writes a resolved gap unconditionally, so every child of a substituted node gains 12px of space the base never had - `normal` is not `0px`, and a `Stack` with no gap prop still emits one. And more fundamentally, a block-level `div` collapses its children's margins while a flex container does not, so even a gap of zero would move the heights. So a `div` that was not already a flex container must not become a `Stack` at all, whatever gap it is given.

**The shift-logbook crash does not reproduce, and the leading explanation is Vite re-optimizing dependencies mid-run - correlation, not proven.** The full converted page renders fine in a clean worktree and fails only on the known geometry diff, with zero occurrences of the error. Searching every log on disk finds the message in exactly two, and one of them is an unrelated settings probe; both carry Vite's mid-run re-optimization warning, and every run that did not crash carries neither. That is what explains the anomaly that never fitted - four structural variants passing while the whole conversion failed - as a function of when the run happened rather than what it contained. Two attempts to force the window failed: deleting an optimized chunk while leaving the metadata claiming it was optimized does not open it, because Vite repairs a missing chunk at startup, so the window is specifically a dependency first discovered during the browser phase, which could not be manufactured from outside Vite's crawler within the budget. The mechanism is therefore recorded as correlation. It is still the best explanation available, it is page-independent, and it is consistent with the earlier `Failed to fetch dynamically imported module` failures, which are the same cache in a different failure mode.

The mitigation is cheap and deferred rather than bundled into a page batch. `vite.config.ts` configures no `optimizeDeps` at all, and the deps observed being optimized mid-run - `@fluentui/react-icons`, `@tanstack/react-table`, `zustand/middleware` - are ordinary declared dependencies, so pre-declaring the browser test deps in `optimizeDeps.include` is the change Vite's own warning prescribes. It is not applied here for two reasons: the exact configuration key has to be verified against the Vitest and Vite documentation rather than assumed, and the proposal places `optimizeDeps` under `test:` where a browser-mode Vitest project may not read it. It belongs in its own task with its own verification - apply, then show that no mid-run re-optimization warning appears across a full browser union run - rather than as an unverified change smuggled into a conversion batch. Also note the operational tension it exposes: `rm -rf node_modules/.vite` protects a worktree run from a poisoned shared cache and simultaneously forces exactly the re-optimization that opens this window, so the two protections pull against each other.

The consequent decision, which reverses the earlier one on the evidence rather than on taste: the card surface has to stay a block-level element carrying `sharedStyles.contentCard`, and the primitive that already renders exactly that is `DetailSurface` - `mergeClasses(sharedStyles.contentCard, className)` on a plain `div`. It currently accepts only `children` and `className`, so it cannot express the padding, minimum height and margins that a card's own style props used to carry. `DetailSurface` therefore gains optional spacing props - `p`, `mt`, `mb`, `minHeight` - using `Stack`'s own vocabulary of spacing-scale names or numbers, each defaulting to nothing so that every existing consumer renders exactly as before. Consumers named: `ShiftPlanDetailPage` and `ShiftLogbookDetailPage`, both of which need a 16px card with a minimum height, and the wider family of nine look-alike detail pages that all declare the same `{12, 16}` shape. What is deliberately NOT done is the alternative of giving `Stack` a block mode or changing its gap default, because either would move callers this workstream has already converted, and not a spacing option on `DetailSectionCard`, because these cards carry their own title in the page's JSX and must not gain a second one.

That baked-in margin is a wart in a shared style rather than a page's fault, and it is worth naming as a candidate for a later cleanup: a surface class that silently adds vertical space makes every caller's rhythm depend on an invisible constant. It is not this workstream's job to change it, because changing it would move every already-converted page, but it should be recorded rather than rediscovered by the next writer who finds a margin they did not write.

The order of attack is fixed by that: try composition out of existing primitives first, with the parity fingerprint deciding, because `DetailSurface` plus a `Stack` with `p` and `minHeight` may already cover a site. Add API to a common primitive only if composition genuinely cannot express the site, only with a second consumer that will land in the same batch, and never as raw px - a spacing-scale option matching `Stack`'s own vocabulary is the shape to reach for, and its default must preserve the current rendering so no converted page moves.

**Stop rule.** If context runs out mid-batch, stop at a committed page boundary and report which pages landed and which did not. A clean partial batch beats a complete-looking one.

**A parity fixture cannot prove a conversion happened, and that is now a rule rather than a caveat.** A fixture is captured from the BASE page, so an unconverted page passes its own parity test trivially - the test proves non-regression and nothing else. This was not theorised; it was demonstrated. During batch 7 a writer's targeted script asserted the wrong occurrence count, raised before writing the page, and the writer mis-read the output as success, so a commit landed carrying the ledger change, the baselines, the fixture and the test but not the converted page. The conversion's absence was caught by two other checks rather than by parity: the ledger entry had been removed while the page still contained its three violations, so the ledger test reported violations missing from the ledger, and `eslint .` would have failed the same way. The correct statement is therefore a conjunction, and all three parts are load-bearing: the ledger entry is gone, `eslint .` is clean so no page-layer construct remains, and the parity test is green against a base capture so nothing moved. Any one of them alone is satisfiable by a page that is wrong in a different way.

**A gate is only a gate if its decision aggregates every check it runs.** The same commit landed because the writer's commit gate printed the results of format, dependencies, unit, lint and type checks, of which several read 1, and then decided on two of them. A script that prints a failure and commits anyway is worse than no script, because it manufactures the appearance of a gate and converts a loud failure into a silent one. Every per-page acceptance list from here has to name one aggregate condition - all checks zero - plus the positive byte assertion the writer then added: `git show HEAD:<page>` must contain the expected number of `DetailSurface` references and zero references to the theme or `makeStyles`. That assertion is cheap, it is what would have caught this directly, and it now sits alongside the parity test rather than replacing it. The broken commit was unpushed and unreported, so it was rewritten with a soft reset. Note the honest wording for that: the commit is unreachable from `main` and no longer in history, but it still exists in the object database and in the reflog, so it should be described as unreachable rather than deleted, and the repository should not be assumed to be free of it until a garbage collection.

**The global backstop already existed, which is why this did not need a repo-wide re-audit.** The ledger test compares every removed entry against the violations actually found, so it fails on any page whose entry was dropped without the page being converted. It runs inside the unit suite, which is part of the final acceptance gate, so a single page's broken commit cannot survive to the end of the workstream - it can only survive if the gate is not run or its output is not read, which is the failure mode described above. The consequence for the remaining pages is small and for the finished ones is reassuring: the earlier batches were reviewed by an independent reader who counted the ledger and ran `eslint .` themselves at a pinned commit, so the conjunction was satisfied at the time.
